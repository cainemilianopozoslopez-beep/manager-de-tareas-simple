# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This is **TaskPulse** (formerly "Gmail Task Manager" / "Pulse Matrix" — same project, since rebranded consistently across the UI), a React + Vite PWA task manager. It is a **standalone frontend**: there is no backend server in the request path — Auth and data live entirely in **Firebase** (Auth + Firestore). The app is live at **https://manager-de-tareas.web.app**, published via Firebase Hosting.

The one exception to "no backend": due-task push notifications need *something* running server-side on a schedule, so there's a `functions/` directory at the repo root — but it's a plain Node script run by a GitHub Actions cron workflow, **not deployed Firebase Cloud Functions** (that needs the paid Blaze plan; deliberately avoided). See "Push notifications" below.

The legacy `../server/` directory (Express + SQLite, dead code predating the Firebase migration) has been deleted, along with the two other unused leftovers from before the `Pulse*` rename, `src/components/Header.jsx` and `Sidebar.jsx` — the active header/sidebar are `PulseHeader.jsx`/`PulseSidebar.jsx`. `src/components/UserMenu.jsx` is a separate, still-active component (the account dropdown), used directly by `PulseHeader.jsx` — don't confuse it with the deleted legacy trio.

## Commands

Run from `client/`:

```
npm run dev       # start Vite dev server (default port 5173)
npm run build     # production build
npm run preview   # preview the production build (port 4173) — needed to exercise the PWA/service worker
npm run lint      # oxlint
npm run test      # node --test on src/taskUtils.test.js (the only client test file)
```

**Testing** uses Node's built-in runner (`node --test`), not Jest/Vitest. Only `taskUtils.js` (pure filter/recurrence/priority logic) is covered. UI components and the Firebase data-access layer (`firebase.js`) are not unit-tested — verify Firestore-touching changes by hand in the browser (or Claude-in-Chrome) against the real project, since there's no emulator wired up.

There's a second, separate `functions/` directory at the **repo root** (not under `client/`) for the push-notification backend — see "Push notifications" below. It has its own `package.json`/`node_modules`:

```
cd functions
npm install
node scripts/run-due-task-check.js               # runs the real due-task scan against production Firestore — needs functions/.env (see .env.example)
node scripts/send-test-push.js subscription.json # sends one push directly, bypassing Firestore, for isolating browser/SW issues
```

Both scripts talk to **real production Firestore/push infrastructure**, not an emulator — there's no local emulation for this (the Firestore/Pub-Sub emulators need a JDK, which isn't installed on the machine this was built on; a plain-script + GitHub Actions design was chosen partly to sidestep that dependency entirely). Be deliberate about what test data you leave behind — clean up any test task/subscription you create by hand afterward.

### Deploying

Run from the **repo root** (`../`), not `client/`:

```
firebase deploy --only hosting          # publish client/dist to manager-de-tareas.web.app
firebase deploy --only firestore:rules  # publish firestore.rules
```

Deploys are **manual** — there is no CI/CD for hosting. `npm run build` must be run in `client/` before `firebase deploy --only hosting` picks up fresh output (`firebase.json`'s `hosting.public` points at `client/dist`). Firebase-generated auto-deploy workflows (`firebase init hosting:github` output — `.github/workflows/firebase-hosting-{merge,pull-request}.yml`, `deploy.yml`) exist on disk but are individually gitignored (see `.gitignore`) and not wired to a GitHub secret; don't re-enable them without asking.

The **push-notification backend is the one thing that *does* auto-run via CI**: `.github/workflows/send-due-pushes.yml` is a real, tracked, in-use GitHub Actions workflow (cron every 10 minutes) — don't confuse it with the gitignored auto-deploy ones above just because they live in the same directory. `.gitignore`'s `.github/workflows/*` entries are listed per-file specifically so this one stays tracked while the unused three stay out.

**Cache headers matter here.** `firebase.json` sets `Cache-Control: no-cache` on `index.html`, `sw.js`, and `manifest.webmanifest`, and `public, max-age=31536000, immutable` on `/assets/**`. This is load-bearing: Vite content-hashes filenames under `/assets/`, so those can be cached forever, but `index.html` (which references the current hashed filenames) and the service worker must always be revalidated — otherwise a deploy can take up to an hour to reach returning visitors who cached the old `index.html` under a looser policy. If you ever touch `firebase.json`, keep this split.

## Architecture

**Single-component state, no router, no state library.** `src/App.jsx` owns essentially all application state (auth, tasks, settings, selection, modals, theme, view, toasts) via `useState`/`useEffect` and passes callbacks down as props to presentational components in `src/components/`. There is no Redux/Zustand/Context — if you need shared state, it goes in `App.jsx` and gets threaded through props.

**Two parallel data paths for tasks — registered vs. guest.** Every task-mutating handler in `App.jsx` branches on `user?.isGuest`:
- **Registered users**: state is Firestore-backed, real-time. A `subscribeUserTasks(user.uid, ...)` `onSnapshot` listener (wired in a `useEffect` keyed on `user`) keeps `allTasks` in sync automatically — mutation handlers just call the Firestore write and let the listener update the UI; they do **not** also update local state by hand (that used to be a bug — see the note on task paths below).
- **Guests**: state lives entirely in the `guestTasks` array (seeded from `DEFAULT_GUEST_TASKS`), mutated in-memory. Nothing touches Firebase. The guest *identity* (`gmail_task_guest_user`) is `sessionStorage`-only and is cleared on logout/tab close, as intended — but `guestTasks` itself is mirrored to **`localStorage`** (`gmail_task_local_tasks`) and that key is never cleared on logout. In practice guest task data quietly survives across guest sessions and browser restarts, even though the guest login screen implies a fresh start each time. Don't assume guest data is ephemeral when debugging.

**Firestore data model — everything lives under `users/{uid}/…`.** `firestore.rules` (repo root) only grants access to `match /users/{userId}/{document=**}` for `request.auth.uid == userId`, and denies everything else by default. `src/firebase.js` mirrors this exactly:
- Tasks: `users/{uid}/tasks/{taskId}` (`subscribeUserTasks`, `addFirebaseTask`, `updateFirebaseTask`, `deleteFirebaseTask`, `batchApplyFirebaseAction`, `exportUserBackup`/`importUserBackup`).
- Settings: `users/{uid}/settings/main` (`getUserSettings`, `updateUserSettings`).

**Do not add a top-level/flat collection for tasks (e.g. a bare `tareas` collection).** An earlier version did exactly that — it bypassed the per-user rule structure entirely, so every read/write was silently permission-denied (infinite "loading" state, no console error) and, had the rules ever been loosened to allow it, would have leaked every user's tasks to every other user. Always write task/setting paths through `users/{uid}/...`, and pass `user.uid` (never `user.username` or `user.email`) as the id segment.

**Filtering / recurrence / priority logic lives in `src/taskUtils.js`.** `filterByTab`/`filterByCategory`/`filterBySearch`/`filterTasks`, `advanceDueDate`/`advanceRecurringTasks`, `getEffectivePriority`/`compareTasksByUrgency`, `getTodayStr`/`dateStrDaysFromToday`. Used for both the guest in-memory path and the registered/Firestore path (post-snapshot), so a sidebar badge count can never disagree with the visible list. There is no server-side copy anymore — `taskUtils.js` is the single source of truth.

**Error-handling convention for Firestore writes: re-throw from the `handleX` function in `App.jsx`, let the modal's `try/catch` react to it.** `handleSaveTask` and `handleSaveSettings` both `console.error` + `showToast(..., 'error')` in their `catch`, then `throw err` — the calling modal (`TaskModal`/`SettingsModal`) awaits the call inside its own `try/catch` and only proceeds to its "success" UI (closing the form, showing a green banner) inside the `try` block, so a failed write can never *also* look like it succeeded. `handleSaveSettings` didn't re-throw until 2026-08-21 — `SettingsModal` showed its "guardado correctamente" banner unconditionally after the `await`, so a failed save produced both the red error toast *and* the green success banner simultaneously. If you add another modal-backed save handler, follow the re-throw pattern from the start rather than copying the pre-fix version.

**`importUserBackup` (firebase.js) chunks writes at 450 per batch, not one batch for the whole file.** Firestore hard-caps a `writeBatch` at 500 operations; a restore with >500 tasks used to fail entirely on `batch.commit()`, and — because the failure surfaced in the same `catch` as `JSON.parse` — got mis-reported to the user as "el archivo no es un respaldo JSON válido" (it was valid; the file just had too many tasks). `App.jsx`'s `handleImportBackup` now parses JSON in its own `try/catch` before calling `importUserBackup` at all, so that distinction holds going forward — don't collapse them back into one `try` block.

**Two independent view concerns — don't conflate them.** `currentTab` (sidebar selection: `inbox`/`pending`, `starred`, `scheduled`, `today`, `week`, `overdue`, `completed`, `trash`) drives **which tasks are visible**, via `filterByTab`. `activeView` (`'matrix' | 'list' | 'calendar' | 'stats'`, also settable from the sidebar and from the mobile bottom nav) drives **which top-level screen renders**: `MatrixView` (Eisenhower 2×2 quadrant board, the default/primary view — this is the "Pulse Matrix" branding), `TaskList`, `CalendarView` (month grid; clicking a day opens the composer prefilled via `TaskModal`'s `initialDate`), or `StatsDashboard` (completion ring, category/priority bars, next-7-days). These two states are orthogonal — e.g. you can be on the `starred` tab while viewing `calendar`.

**Category and search filters apply everywhere; `currentTab` only applies to List.** `App.jsx` computes `globallyFilteredTasks` (category + debounced search applied to `visibleAllTasks`, same list the sidebar badge counts are derived from) and passes *that* — not raw `visibleAllTasks` — into `MatrixView`, `CalendarView`, and `StatsDashboard`. `TaskList` gets the further tab-filtered `visibleTasks` instead. This split is deliberate, not an oversight to "complete": `currentTab` is a List-specific "which folder" concept (e.g. Papelera), while Matrix/Calendar/Stats are meant to show one global picture — searching or filtering by category should visibly affect every view, but switching to the "Vencidas" tab shouldn't suddenly hide tasks from the Matrix board. (Until 2026-08-21 this wasn't the case at all — those three views got the *entirely* unfiltered task list, so the search bar visibly did nothing outside List view.)

**Eisenhower quadrant placement is derived, not stored — `getEisenhowerQuadrant` (taskUtils.js) recomputes it from `starred`/`priority`/`dueDate` on every render.** `isHighImportance = starred || priority is 'urgente'/'alta'`; `isUrgent = dueDate <= tomorrow`. This means **`starred` alone is enough to force a task into Q1/Q2 regardless of priority** — a starred task can never land in Q3/Q4 unless `starred` is explicitly cleared too. `App.jsx`'s `handleMoveToQuadrant` (used by both HTML5 drag-and-drop and the `TaskItem` "move" button below) sets `starred: false` on its Q3/Q4 branches for exactly this reason; Q4 additionally clears `dueDate`/`dueTime` entirely (not just priority) — a task due today/tomorrow stays `isUrgent` no matter what priority you give it, so without clearing the date it lands in Q3 instead. If you add a fifth way to move a task between quadrants, it needs the same two clears or it'll reproduce this bug (found live-testing the fix for the first half of it — reading the code alone didn't surface the date half).

**Matrix drag-and-drop is native HTML5 DnD (`draggable`, `onDragStart`/`onDragOver`/`onDrop` + `dataTransfer`) and does not work on touch at all**, in any mobile browser, with no polyfill — a hard platform limitation, not a bug to "fix" in this codebase's own code. `TaskItem` accepts optional `onMoveToQuadrant`/`currentQuadrantId`/`quadrants` props (only passed from `MatrixView`, not `TaskList`) that render a "move" button + dropdown as a touch- and keyboard-accessible alternative, calling the same `handleMoveToQuadrant` handler as drag-and-drop. Don't remove this thinking drag-and-drop alone is sufficient — it's the *only* way to move a task between quadrants on a phone.

**`CalendarView` day cells open the composer directly on click — no confirm dialog.** There used to be a `window.confirm()` before calling `onCompose`; removed 2026-08-21 because `onCompose` only opens `TaskModal` prefilled with that date, it doesn't create or change anything by itself, so the confirm was pure friction with no actual data-loss risk to guard. Don't add one back without a real destructive action behind it. The "+N más" overflow indicator is a real popover now (`expandedDay` state, one open at a time, listing every task for that day, each clickable into `onEdit`) — it used to be inert text with only `stopPropagation()` on click.

**Tasks carry subtasks.** Each task may have `subtasks: [{ id, text, done }]`, edited in `TaskModal`, shown as a `done/total` progress badge in `TaskItem`/`MatrixView` cards.

**Bulk selection + batch action.** `App.jsx` holds `selectedIds` (a `Set`), cleared whenever the visible set changes (tab/category/search). `batchApplyFirebaseAction(uid, ids, action, value)` applies one action (`done`/`pending`/`trash`/`restore`/`category`/`delete`) to many ids in a single Firestore batch write; the guest path mutates `guestTasks` in memory the same way. `TaskList`/`MatrixView` render a contextual bulk-action bar.

**Keyboard shortcuts.** A global `keydown` listener in `App.jsx`: `c` compose, `/` focus search (`id="task-search-input"`), and a `g`-then-initial chord to jump views. Ignored while typing in a field or when any modal is open.

**Mobile layout is a separate nav surface, not a responsive reflow of the desktop sidebar.** Below the `860px` breakpoint (`src/index.css`), a Gmail-style bottom nav bar (`.mobile-bottom-nav`, 4 buttons wired to `setActiveView`) and a floating compose button (`.mobile-fab-btn`, opens `TaskModal`) appear; `PulseSidebar` becomes an off-canvas drawer (`isSidebarOpen`/`onToggleSidebar` from `PulseHeader`) instead of disappearing. If you add a new `activeView`, wire it into both `PulseSidebar`'s desktop switcher and the `.mobile-nav-item` buttons in `App.jsx`, or mobile users will have no way to reach it.

**Auth is real Firebase Auth**, email/password only (no Google sign-in — it was deliberately removed). `loginWithEmail`/`registerWithEmail`/`resetUserPassword` (`src/firebase.js`) wrap `signInWithEmailAndPassword`/`createUserWithEmailAndPassword`/`sendPasswordResetEmail`; `Login.jsx` has a "¿Olvidaste tu contraseña?" link that calls `resetUserPassword` and shows Firebase's own password-reset email flow (no custom email template involved). `translateFirebaseError` maps Firebase's `err.code` values to Spanish messages — add new codes there rather than showing raw Firebase error text. Session restore on reload goes through `subscribeAuth` (`onAuthStateChanged`), not just the `localStorage` cache, so login survives across devices, not only reloads. A registered-user record cached from before the Firebase migration (no `uid` field) is treated as invalid and discarded on load.

**Two independent notification mechanisms — don't conflate them.** (1) **Browser `Notification` API**: client-side only, gated on permission, polled every 10s in `App.jsx` against `settings.scheduledTime` (daily summary) and each task's `dueTime` (per-task). Only fires while a tab is open — closes with the tab. (2) **Web Push**: see "Push notifications" below — the one that actually reaches the user with every tab/browser closed. They share the browser's `Notification.permission` (Push needs it too, to display anything), but push additionally needs a `PushManager` subscription and, for iOS, an installed PWA. The Settings panel shows both as separate toggles for this reason — enabling one does not enable the other.

Gmail/SMTP-based email sending was removed entirely (mid-2026) — it never worked (there was no server to hold credentials safely) and was letting users type a real Gmail app password into a field that got stored in Firestore in plain text for a feature that always failed on send. `EmailPreviewModal`, `emailTemplate.js`, the "Correo Gmail"/"Ambos" notification modes, and the `senderEmail`/`senderPass`/`recipientEmail` settings fields are all gone. Don't resurrect a client-stored password field if email gets rebuilt — hold credentials server-side (the GitHub Actions workflow used for push, below, is exactly this pattern already).

**Push notifications** (added 2026-08-20/22). Client: `src/push.js` — `subscribeToPush(uid)`/`unsubscribeFromPush(uid)` wrap `PushManager` + a VAPID key (`VITE_VAPID_PUBLIC_KEY` env var), storing one Firestore doc per device under `users/{uid}/pushSubscriptions/{id}` (keyed off a hash of the endpoint, so re-subscribing the same device overwrites rather than duplicates). `isPushSupported()` checks for `serviceWorker`/`PushManager` in the browser — **this returns `true` in a plain iOS Safari tab too**, even though subscribing there always fails; `isIos()`/`isRunningStandalone()`/`needsIosInstallForPush()` exist specifically to catch that case before it produces a confusing error (`subscribeToPush` throws a clear Spanish message if called there, and `SettingsModal`'s push panel shows "Agregar a inicio" instructions instead of the Activar button when `needsIosInstall` is true — but still shows Desactivar if a subscription already exists, since disabling should never be blocked). `App.jsx`'s `enablePushNotifications`/`disablePushNotifications` wire this to the UI and are gated on `!user.isGuest` — guest tasks aren't in Firestore, so there's nothing for the backend below to find due.

Backend: **not a Firebase Cloud Function** (would need the Blaze paid plan; explicitly rejected as a cost the user didn't want). Instead, `functions/scripts/run-due-task-check.js` is a plain Node script — no `firebase-functions` dependency at all — run every 10 minutes by `.github/workflows/send-due-pushes.yml` via GitHub Actions cron (free because the repo `manager-de-tareas-simple` is public). It authenticates to Firestore via a service-account key and to the push service via the VAPID keys, both passed as GitHub Actions repo secrets (`FIREBASE_SERVICE_ACCOUNT_JSON`, `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_CONTACT_EMAIL`) — **never committed**, see `functions/.env.example` for the local-testing equivalent (`functions/.env`, gitignored). It walks `users/*/tasks` **per-user subcollection** (`db.collection('users').listDocuments()` then a scoped `where('dueDate', '==', todayStr)` per user) rather than a top-level `collectionGroup('tasks')` query — the latter needs a manually-provisioned composite Firestore index that doesn't exist; per-user queries use Firestore's automatic single-field indexes with zero setup, at the cost of one extra read per user (fine at this scale). Dedup uses a `pushNotifiedAt` field persisted directly on the task doc (set after a successful send) — this is a *different* mechanism from the client's `notifiedTaskKeysRef` (in-memory, one tab session only) and is the one that actually matters for not re-notifying across the script's independent 10-minute runs.

`functions/scripts/send-test-push.js` is a separate, never-deployed helper for manually testing the push pipeline end to end without waiting for the scheduled workflow — sends one push directly to a subscription JSON you paste in, using the VAPID keys from `functions/.env`. Useful for isolating "is the browser/SW side broken" from "is the due-task-detection logic broken" before assuming the harder-to-debug one.

**Recurring tasks and push — the two are coupled in a way that isn't obvious.** `taskUtils.js`'s `advanceRecurringTasks` computes the rolled-forward `dueDate` for an overdue recurring task, but that function itself only returns a new in-memory array — it never touches Firestore. For **registered** users, `App.jsx`'s `onSnapshot` success callback now (as of 2026-08-21) diffs the advanced copy against the raw snapshot and fires `updateFirebaseTask(uid, id, { dueDate, done: false })` for whichever tasks actually rolled forward, specifically so the *stored* `dueDate` in Firestore matches what's on screen. Before that fix, a recurring task's Firestore `dueDate` stayed frozen on its first-ever occurrence forever — invisible in the app itself (which always recomputes for display), but fatal for `run-due-task-check.js` above, which reads `dueDate` straight from Firestore with zero awareness of this client-side rollover logic, so it could never again match `dueDate == todayStr` after the first occurrence. If you touch either the recurrence logic or the push script, keep this coupling in mind — a change that looks correct in the app's UI can still silently break push for recurring tasks specifically. Guests don't need this: `advanceRecurringTasks`'s result is what gets mirrored to `localStorage` directly, so it's already "persisted" for that path, and guests have no push subscriptions to matter anyway.

**Theming** is CSS-variable-based light/dark: `App.jsx` sets `data-theme` on `<html>` and persists the choice (`localStorage`, and to `users/{uid}/settings/main` for registered users); variables are in `src/index.css` under `:root` (light) and `[data-theme="dark"]` (dark). Avoid hardcoded hex colors — use `var(--gmail-*)`.

**Styling is inline `style={{}}` objects throughout components** (aside from `lucide-react` icons, badge/pill classes, and the mobile-nav/FAB classes in `index.css`). Follow this pattern rather than introducing CSS modules or a component library. Keyboard focus is restored via a global `:focus-visible` rule.

**Modals share an accessibility hook.** `src/useModalA11y.js` gives every dialog (`TaskModal`, `SettingsModal`, `ProfileModal`) Escape-to-close, a focus trap, focus-on-open, and focus-restore-on-close. Wire it with `role="dialog"`, `aria-modal`, an `aria-label`, and `tabIndex={-1}` on the dialog container.

**Installable as a PWA — re-enabled 2026-08-22, on purpose.** It was previously removed deliberately (no manifest link, no installability), but got turned back on specifically because **Web Push on iOS Safari only works for a site added to the Home Screen — never in a regular browser tab, no exception.** `index.html` links `manifest.webmanifest` (the file itself, and the icons, were already on disk the whole time, just unlinked/orphaned) and carries `apple-mobile-web-app-capable`/`apple-mobile-web-app-status-bar-style`/`apple-mobile-web-app-title` meta tags. If push notifications ever get ripped out entirely, installability could go with it — but don't remove just the manifest link while push stays, that silently re-breaks iOS.

The service worker (`sw.js`) registers only in production (`main.jsx`, guarded by `import.meta.env.PROD`), so offline/fast-load *and* push behavior are exercised with `npm run build && npm run preview`, not the dev server (`navigator.serviceWorker.ready` never resolves in dev — a push "Activar" click will hang forever there, not fail loudly). `sw.js` is network-first for navigations, stale-while-revalidate for other same-origin GETs, ignores cross-origin requests (Firebase's own domains) entirely, and additionally handles `push` (shows the OS notification + posts a `push-received` message to any open window client, which `App.jsx` just `console.log`s — a debugging hook, not a feature) and `notificationclick` (focuses an existing tab or opens one). See the cache-headers note under Deploying — the SW's network-first strategy only works if `index.html` itself isn't being served stale by Hosting/the browser HTTP cache.

**Dates are local, not UTC.** Use `getTodayStr`/date helpers in `taskUtils.js`, which derive `YYYY-MM-DD` from local date components. Do **not** use `new Date().toISOString().slice(0,10)` for "today" — that's UTC and flips the day at a non-midnight local hour, breaking due-today, recurrence, and the scheduled filter.

**Search is debounced.** `searchQuery` updates instantly (UI + in-memory counts), but `debouncedSearch` (300ms) is what the guest-path filter and any future server-style fetch would key off of.
